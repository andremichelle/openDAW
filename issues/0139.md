## Summary
The reporter asks for modulation sources that can drive any device parameter:
1. Envelope follower (amplitude of a chosen signal).
2. LFO.
3. MSEG (free drawn envelope).
4. Step modulator (trance gate style).
5. XY controller mapping parameters to two axes.
6. Key tracking.
7. Velocity.

No comments.

## Current state
A project level modulation system exists and is in production (plan `plans/modulations.md`, phases 1 to 5 done, phase 6 partly done).
1. Schema: modulators live in `rootBox.modulators` (`packages/studio/forge-boxes/src/schema/std/RootBox.ts:27`), assignments are `ModulationBox` (`packages/studio/forge-boxes/src/schema/std/ModulationBox.ts`) with source, target, depth.
2. Modulator types today: `LfoModulatorBox`, `StepsModulatorBox`, `RandomModulatorBox`, `MacroModulatorBox` (`packages/studio/forge-boxes/src/schema/std/modulators/`, shared fields in `ModulatorFactory.ts:6`).
3. Engine: `crates/engine/src/modulation.rs:250` `ModulatorKind {Lfo, Steps, Macro, Random}`, all position derived (`value_at`, `crates/engine/src/modulation.rs:310`).
4. Modulator parameters are automatable and MIDI learnable (commits `adbedb318`, `4440c6305`).

So items 2 (LFO) and 4 (steps) are done. Macro covers a single axis knob. Key tracking exists only inside devices (for example Vaporisateur `filter-keyboard`, `packages/studio/forge-boxes/src/schema/devices/instruments/VaporisateurDeviceBox.ts:79`), and a Velocity MIDI effect exists (`packages/studio/forge-boxes/src/schema/devices/midi-effects/VelocityDeviceBox.ts`), but neither is a modulation source.

## Analysis
`plans/modulations.md:393` lists what the current design does not cover:
1. Envelope follower needs audio access inside the modulator, a different evaluation path from the position derived shapes.
2. Note triggered envelopes (MSEG retriggered per note, sidechain style) need note or transport events.
3. Per voice sources (velocity, key tracking, per voice envelopes) need per voice parameter resolution, a large ABI change, explicitly out of scope.

An MSEG that runs on song position (free or synced, like the LFO) fits the existing model: one new box with a point array (like the 64 slot step array at field 20 of `StepsModulatorBox`) plus a `ModulatorKind` variant. An XY pad is two Macro values with a 2D editor, also within the existing model.

## Possible solution
1. MSEG (position driven): new `MsegModulatorBox` via `ModulatorFactory`, point list (position, value, curve), rate sync and absolute like the LFO, new `ModulatorKind::Mseg` in `crates/engine/src/modulation.rs`, editor in the modulation panel.
2. XY: new `XyModulatorBox` with two outputs, or two Macro modulators driven by one XY editor. Two outputs need the assignment to pick an output index (new `ModulationBox` field).
3. Envelope follower: a modulator that reads a chosen audio unit's output level. Needs an engine path where the modulator table is evaluated after that unit has rendered, plus cycle handling. Separate plan.
4. Velocity, key tracking, note triggered MSEG: per voice modulation. Needs a separate design (per voice parameter resolution through the device ABI). Separate plan, likely out of scope for now.

## Complexity
large. Items 1 and 2 are medium each (forge-boxes schema, adapters, `crates/engine/src/modulation.rs`, `crates/studio-boxes` registry, modulation panel UI, scripting, tests). Items 3 and 4 are large (engine render order, device ABI for per voice values).

## Open questions
1. Should this issue be split into one issue per modulator type, closing the LFO and steps parts as done?
2. Is per voice modulation (velocity, key tracking) wanted at all, given it is out of scope in `plans/modulations.md`?
