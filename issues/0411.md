## Summary
Nano and the Playfield slot player should become interchangeable, so that Playfield slots can eventually be replaced by Nano instances. The issue asks for a plan.

## Current state
1. The plan exists: `plans/playfield-nano.md` (written 2026-11-02, dry run 2026-11-03). Each pad becomes an `InstrumentCompositeCellBox` holding a Nano plus its own midi-fx and audio-fx chains. The Playfield routes notes by the cell `index` (pad key) and remaps them to a per pad `key` (default 60). The slot player (`PlayfieldSampleBox`, `crates/stock-devices/device-playfield-sample`) is retired and old projects migrate on load.
2. Done: Nano feature gaps closed in 0aa4db2d8 (#467): Mono/Poly, Pan, One-Shot, Fixed pitch, choke fade, 64 voice steal oldest. Phase 1 of the plan, the general Note Filter MIDI effect, is on main in 0fe8e500c (`crates/stock-devices/device-note-filter`, `packages/studio/forge-boxes/src/schema/devices/midi-effects/NoteFilterDeviceBox.ts`).
3. Not done: plan phases 2 to 6. The Playfield still routes through `SlotRoute` at the base of the pull chain (`crates/engine/src/lib.rs:1442`) and still uses the slot player.
4. No commits reference #411 directly.

## Analysis
1. The plan lists the remaining differences between Nano and the slot (envelope lengths, release shape, fast release, gain order, Gate Off end, reverse length, Gate On end fade, loop without crossfade, tune rounding, sub frame windows, broadcast addresses). These only matter for a bit identical migration of old projects.
2. Exclude today sees the raw pitch while the slot filter runs after the unit midi-fx. The new routing step (after the Playfield midi-fx, before the pad midi-fx) removes that mismatch.
3. Migration must move every incoming pointer (automation, modulation, MIDI learn, sidechain, selection) from slot to cell or Nano, run in presets and the clipboard too, and be safe when two live room clients load at once.
4. About 40 TS files touch Playfield boxes, including the SDK adapter API and scripting `PlayfieldSlot`, so external SDK users are affected.

## Possible solution
Follow `plans/playfield-nano.md`:
1. Phase 2: decide on open decision 1 (slot compatible mode in Nano, tolerance, or keep the slot player for old projects), then close the chosen Nano gaps with a parity test.
2. Phase 3: cell based Playfield spec in crates/engine, a routing step between unit midi-fx and cell midi-fx with remap, exclude, owner gating, pitch table for releases, mute flag, pad sidechain, meters, native tests.
3. Phase 4: schema (`pads` field on `PlayfieldDeviceBox`, `exclude` and `key` on `InstrumentCompositeCellBox`), `migratePlayfieldDeviceBox` with all pointers, preset and clipboard hook, `playfield.od` render test.
4. Phase 5: UI, SDK and scripting move to cells and Nano, with old names kept working.
5. Phase 6: any instrument on a pad.

## Complexity
large. crates/engine (routing, composite spec), crates/stock-devices (Nano), box schema and migration (forge-boxes, studio-core), adapters, Playfield and cell editors in app/studio, scripting, SDK, core-wasm tests.

## Open questions

2. How many held notes the pad router tracks (plan open decision 2)?
3. Removing a sample from a pad: delete the cell or keep an empty pad (plan open decision 3)?
