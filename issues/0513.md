## Summary
Freezing an audio unit does not survive reloading the project. The frozen state should be stored in the project data and the units should be frozen again when the project loads.

## Current state
1. Freeze is session state only. `AudioUnitFreeze` keeps frozen units in an in memory map of rendered `AudioData` (`packages/studio/core/src/AudioUnitFreeze.ts:17`). Nothing is written to the box graph or to storage.
2. `freeze()` renders a stem of the unit (effects included, channel strip skipped) on a copy of the project through `OfflineEngineRenderer` with a progress dialog, then hands the PCM to the engine with `engine.setFrozenAudio` (`AudioUnitFreeze.ts:91` to `:157`).
3. Changing BPM or tempo automation unfreezes all units (`AudioUnitFreeze.ts:24` to `:27`).
4. A worklet restart replays the frozen PCM (`AudioUnitFreeze.ts:42`, called from `packages/studio/core/src/project/Project.ts:356`). This is the only persistence and it lives as long as the `Project` instance.
5. While frozen, the UI blocks region editing and capture (`packages/app/studio/src/ui/timeline/tracks/audio-unit/regions/RegionsArea.tsx:103`, `packages/studio/core/src/capture/CaptureDevices.ts:56`). The freeze and unfreeze menu entries are in `packages/app/studio/src/ui/timeline/tracks/audio-unit/headers/TrackHeaderMenu.ts:86` and `packages/app/studio/src/ui/mixer/ChannelStrip.tsx:169`.
6. `AudioUnitBox` has no frozen field (`packages/studio/forge-boxes/src/schema/std/AudioUnitBox.ts`). The WASM engine side is in `crates/engine/src/frozen.rs`.
7. No commits reference #513.

## Analysis
1. Two ways to persist: store only a flag and re-render on load, or store the rendered PCM as a sample and reload it.
2. Storing PCM adds a cache that can go stale: UI editing is blocked, but scripting, a live room peer, undo of earlier steps or a changed sample can still change the unit's content. It also has to travel with project bundles and cloud backups.
3. Re-rendering on load is always correct, costs one offline render per frozen unit at load, and needs no sample management. The CPU saving during playback stays.
4. A box field makes freeze undoable and visible to live room peers. Each peer would then freeze locally, which is consistent but means each client renders. Freezing is currently not an undo step, so the field should be written outside undo or accepted as one.

## Possible solution
1. Add `frozen` (boolean, new field key) to `AudioUnitBox`. Regenerate boxes and the Rust registry if the engine reads the box list.
2. `freeze()` and `unfreeze()` set the field in a transaction. `AudioUnitFreeze` subscribes to the field of every audio unit and renders or releases the PCM when it changes, so load, undo and live room peers follow the same path.
3. On project load, after the worklet is ready, render all units with `frozen = true` one after another under a single progress dialog. If a unit can no longer be frozen (sidechain dependents, sink), clear the field and notify.
4. Keep the tempo unfreeze, now also clearing the field.
5. Optional later: cache the rendered PCM in OPFS keyed by a hash of the unit's content to skip the render on load.
6. Tests: field set on freeze, cleared on unfreeze and tempo change, load triggers render, undo restores.

## Complexity
medium. Box schema (forge-boxes, boxes, Rust registry), `packages/studio/core/src/AudioUnitFreeze.ts`, project load in studio-core, tests. No engine DSP change.

## Open questions
1. Re-render on load, or store the rendered audio as a sample in the project?
2. Should freeze become an undo step and sync to live room peers, or stay local per client?
