## Summary
When `getUserMedia` rejects, arming (directly, by a monitoring mode or by a recording start) left the capture armed with no stream and an unhandled `Errors.Warning`. The input never opened again until the track was disarmed and armed.

## Fix
1. `CaptureAudio` opens through `#openArmed`: a refused input (`Errors.Warning`) disarms and is reported once through `RuntimeNotifier.info`, anything else is rethrown. A refusal after the user disarmed stays silent. The monitoring mode is kept, so it resumes when the user arms again.
2. `prepareRecording` disarms and rethrows, `Project.startRecording` reports the Warning through the notifier (one dialog in the studio, as before).
3. `measureRoundTrip` opens through `#openArmed` as well (also when the track was armed already) and rejects with `Errors.AbortError` after a refusal, `LatencyMeasurement` shows no second dialog.
5. A recording started while the permission prompt is open: the refusal is reported once, `prepareRecording` rejects with an abort, `RecordingSession.start` cleans up and passes the abort on, `Project.startRecording` ignores it.
6. `RecordingSession.start` waits for every capture (`Promise.allSettled`) and shows the first failure that is not an abort, so one capture's abort cannot hide another's refusal. Cancelling the output latency question rejects with an abort, so no Warning follows the user's own cancel.
4. `RecordingSession.start` no longer doubles the "Error:" prefix.
Live rooms: `armed` is local there (`Capture.#storeArmed`), the disarm affects only this client. Tests: `CaptureAudio.test.ts` (three cases).

## Progress
1. Fixed on next-release, uncommitted.
2. Chrome with a refusing `getUserMedia`: arming shows one Warning, the track is disarmed, no unhandled rejection. Arming while a refusal is pending and pressing Record: one Warning, nothing recorded. Arming again with the input available opens it and the kept With Effects monitoring resumes.
