## Summary
The reporter asks for a light theme as an alternative to the dark UI. MVP: a switch between dark and light, a default taken from the browser (`prefers-color-scheme`), and the choice saved. Later possibly an accessibility section (font scaling, custom color variables). The attached screenshot is Ableton Live with a light theme as reference: panels close to white, text close to black, a beige or vintage tinted background, yellow and orange accents.

## Current state
1. A color scheme preference exists since commit 2747af90a: Preferences > Appearance offers Classic, Modern and High Contrast (`packages/studio/enums/src/Colors.ts:3-32`, `packages/studio/core/src/StudioSettings.ts:46`). All three are dark schemes. "contrast" is a brighter dark scheme, not a light one.
2. The schemes only change the eleven neutral colors. Accents (blue, green, yellow, cream, orange, red, purple) are fixed (`Colors.ts:41-50`).
3. `boot.ts` writes the neutrals as `--color-*` CSS variables on every surface when the preference changes (`packages/app/studio/src/boot.ts:169-172`, `Colors.ts:66-71`). The choice is persisted with the other studio settings.
4. `:root` hard codes `color-scheme: dark` (`packages/app/studio/src/colors.sass:2`).
5. The plan `plans/color-schemes.md` lists the cleanup needed even for dark schemes: hard coded greys in sass, canvas painters that cache colors, derived colors. It asks whether a lighter scheme is planned (open question 2).
6. No `prefers-color-scheme` handling exists.

## Analysis
A light theme is not just another row in `Neutrals`, because the code assumes "neutral lightness goes up = text, goes down = surface" in many places that are not variables:
1. About 290 `rgba(white, x)` / `rgba(black, x)` literals in the studio sass (brighteners, darkeners, separators, `$BRIGHTENER` / `$DARKENER` in `colors.sass:7-8`, diagonal stripes in `colors.sass:16`). On a light surface these become invisible or inverted.
2. Canvas painters (timeline, waveforms, meters, curves, device editors) use `Colors.*` and literal colors with opacity, tuned for dark surfaces.
3. The accents are light pastels (yellow lightness 84, cream 83, green 69). Used as text or thin lines on near white they lack contrast. A light theme needs darker accent variants, so accents must become scheme dependent too.
4. Track and region colors are hue palettes with lightness chosen for dark backgrounds.
5. WebCLAP panels and script views receive `--color-*` but may contain their own dark assumptions.

## Possible solution
1. Finish `plans/color-schemes.md` checks 1 to 3 first: move every literal grey and white/black overlay in sass to variables (for example `--color-overlay-up`, `--color-overlay-down`, `--color-line`), and make canvas painters read colors at paint time.
2. Make accents part of the scheme (`Colors.ts`), so a light scheme can use darker accents.
3. Add a `light` scheme row with inverted neutrals (bright = near black text, panel backgrounds near white) and set `color-scheme: light` on `:root` for it.
4. Add an "auto" option that follows `matchMedia("(prefers-color-scheme: dark)")` and listens to its change event.
5. Review track/region color generation and the device editors per area, with browser checkpoints.

## Complexity
large. Touches `packages/studio/enums/src/Colors.ts`, `StudioSettings`, most `.sass` files under `packages/app/studio/src`, many canvas painters in the timeline, mixer and device editors, the manual, and possibly WebCLAP and script views. No engine or schema changes.

## Open questions
1. Is a light theme wanted at all, given the plan's open question about further schemes?
2. Should accents stay identical across schemes (current rule in the plan) or may a light scheme change them?
