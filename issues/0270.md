## Summary
The reporter wants to automate turning audio effects on and off. André noted that a disabled effect is removed from the audio graph, that an automated switch should fade click free in both directions, and asked whether an effect should start clean (empty delay lines) when turned on again. The reporter answered yes, clear the memory.

## Current state
1. Every audio effect box has `enabled` as a plain boolean without pointer rules, so it cannot take automation (`packages/studio/forge-boxes/src/schema/std/DeviceFactory.ts:30`, same for MIDI effects at `:12` and instruments at `:21`). Compare the automatable `mute` (`packages/studio/forge-boxes/src/schema/std/AudioUnitBox.ts:22`).
2. The power button toggles the field directly, no automation context menu (`packages/app/studio/src/ui/devices/DeviceEditor.tsx:159`).
3. In the engine, a disabled effect is skipped in the chain wiring (`crates/engine/src/audio_unit/mod.rs:103`). A toggle marks the unit for a re-wire through a targeted monitor (`crates/engine/src/audio_unit/mod.rs:382`, `:677`). The switch is a hard cut and keeps the effect's DSP state.
4. The device ABI already has `reset` to clear runtime state (`crates/abi/src/lib.rs:1814`), today called on transport stop.
5. Precedent for automated on/off in the engine: composite entry mute is bound as static, automated and modulated (`crates/engine/src/effect_composite.rs:423`).
6. No commits reference the issue. An older analysis is at `plans/issues/270-automate-effect-enable.md`, it refers to the removed TS processors.

## Analysis
1. Re-wiring is a reconcile step, not a per sample operation, so driving it from automation would be late and click. The bypass must become a signal level operation: keep the effect wired and crossfade between its input (dry) and its output.
2. Turning on with a clean state means calling `reset` on the effect at the moment the fade in starts, which must happen on the audio thread inside render, while `reset` is documented as "called outside render". Each device's reset must be checked to be allocation free and cheap enough.
3. An effect that is off still costs CPU if it stays wired. After the fade out it can skip `process` until it is turned on again.
4. Latency compensation: an effect with latency (Maximizer, Compressor lookahead) needs a dry path delayed by the same amount during the crossfade.

## Possible solution
1. Schema: add `pointerRules: ParameterPointerRules` to `enabled` in the three attribute sets in `DeviceFactory.ts`. Same key and type, so old projects load unchanged.
2. Adapters: register `enabled` as a boolean parameter so the automation menus can target it, and wire the power button with the parameter context menu.
3. Engine: wrap each chain member in a bypass stage with a short crossfade (a few ms) driven by the resolved `enabled` value at the update clock. On off to on, call the device's `reset` and fade in. After a full fade out, skip the device's process.
4. Keep the current re-wire path for plain user toggles only if bit identical output is required. Otherwise route both through the bypass stage.
5. Tests in `packages/studio/core-wasm/test`: automated toggle mid block, no clicks, delay tail cleared on re-enable, latency compensated dry path.

## Complexity
large. Box schema (`packages/studio/forge-boxes`), adapters (`packages/studio/adapters`), device editor (`packages/app/studio`), engine chain wiring (`crates/engine/src/audio_unit`), ABI reset semantics (`crates/abi`), and every stock device's reset checked.
