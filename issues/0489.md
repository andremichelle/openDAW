## Summary
André's proposal: a new modulator type, Script, written like Werkstatt, Apparat and Spielwerk.

1. Use cases: a drawable looping curve synced to tempo, chaotic or physics motion (Lorenz, bouncing ball, spring), stepped logic (Euclidean, probability, Turing machine), transport driven sources (shape per bar, ramp over a section), several outputs from one script (X and Y of a 2D path).
2. Behaves like every modulator: assignments with depth, enabled, bipolar, amount, automatable.
3. Same header as the script devices: `@param`, `@collection`, `@buffer`, `@group`.
4. The processor returns one value per update clock tick, 0..1 or -1..1 when bipolar, and can read transport position, tempo and playing state.
5. Custom views: `@view` inside the modulator panel, `@window` in a floating window, `@stream` sends the output to the view for a live trace.
6. Same code editor, compile errors and paste-and-run as the script devices.
7. Open: one output or several named outputs. How much space a view gets in the tab.
8. Not planned: audio or MIDI input, because modulators are evaluated once per quantum before the audio graph.

## Current state
1. Nothing implemented. Modulator kinds are LFO, Steps, Random and Macro (`packages/studio/forge-boxes/src/schema/std/modulators/`).
2. Common modulator fields (collection, assignments, label, enabled, index, tracks, bipolar, amount) come from `ModulatorFactory` (`packages/studio/forge-boxes/src/schema/std/modulators/ModulatorFactory.ts:6` to `:23`), so a new box gets the assignment behaviour for free.
3. Engine: `ModulatorKind` is a closed Rust enum (`crates/engine/src/modulation.rs:249` to `:253`), values computed by `value_at` (`:310`) and advanced by `advance(delta_seconds, delta_pulses)` (`:323`). Box names map to kinds in `crates/engine/src/lib.rs:2550` to `:2555`, where an unknown name falls back to an LFO, so a new box would silently play as an LFO until it is added there.
4. Script infrastructure to reuse: the script bridge runs user JS from the engine via `host_script_*` imports (`packages/studio/core-wasm/src/script-bridge.ts:212` to `:229`), with parameters, collections, buffers and data snapshots. Script views (`@view`, `@window`, `@collection`, `@buffer`, `@stream`) are implemented for the devices (`plans/script-views.md`, commits c9337aaf1, 32530a9ea). Dynamic parameters as child boxes are bound in `crates/engine/src/script_device.rs:39`.

## Analysis
1. The modulator runs once per quantum (per update tick) in the engine, not inside a device side module. A Script kind needs a host call from `modulation.rs` into the script bridge, a new import such as `host_script_modulate(handle, position, bpm, flags) -> value(s)`, called during the per quantum refresh (`crates/engine/src/modulation.rs:598`).
2. Script parameters: the modulator needs a `parameters` hub with `WerkstattParameterBox` children like the script devices, bound through `observe_script_params` so they are automatable and modulatable.
3. Multiple outputs: the assignment model points at one modulator box (`assignments`, field 2). Named outputs would need either child output boxes that act as sources, or one box per output. One output keeps the first version simple.
4. Views: the modulator panel in the tab needs a host for the script view iframe with a fixed height, `@window` for larger UIs (consistent with "editors never scroll").
5. Determinism: offline render and live rooms must run the same script, as with the script devices.

## Possible solution
1. Schema: `ScriptModulatorBox` via `ModulatorFactory` with `code`, `parameters` hub, `records` and `buffers` hubs (same keys as Werkstatt where possible).
2. Engine: `ModulatorKind::Script` holding a bridge handle, map the box name in `lib.rs:2550`, call the new host import in the per quantum refresh, broadcast the value for `@stream`.
3. Bridge: a `modulatorProcessors` registry and a `KIND_MODULATOR` in `script-bridge.ts`, processor API `process({position, bpm, playing}) -> number`.
4. UI: modulator panel with the code editor button, compile errors and view host, reusing the script device editor parts.
5. Version 1 with one output. Named outputs later as child source boxes.
6. Tests: Rust test that a script modulator drives an assigned parameter, TS test for header parsing and the bridge call.

## Complexity
large. New box (forge-boxes, generated Rust registry), engine modulation kind plus a new host import, script bridge, modulator panel UI with views, manual. Cross-layer.

## Open questions

2. Height of a script view inside the modulation tab compared to a device panel?
