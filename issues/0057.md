## Summary
The reporter wants to drag an effect (for example a reverb) out of one track's chain onto another track, with Alt+drag copying it. André suggested hovering over a track header until the device panel switches to that unit. The reporter agreed and also asked for a faster way: drop the effect directly on the track header and append it to the end of that track's chain. André closed the issue in favour of cut and paste, the reporter asked to reopen because cut and paste is not intuitive, and it is open again.

## Current state
1. André's variant exists. Holding any device drag over a track header for one second switches the device panel to that unit (`packages/app/studio/src/ui/timeline/tracks/audio-unit/headers/HoverEditSwitch.ts:7`, `:20-41`, wired in `AudioUnitTrackHeader.tsx:94` and `:139`). It came with commit 23494659a (fixes #403).
2. Once the panel shows the other unit, dropping an existing effect there already moves it, or copies it with the copy modifier (`packages/app/studio/src/ui/devices/DevicePanelDragAndDrop.ts:180-201`, using `ProjectApi.copyEffects` at `packages/studio/core/src/project/ProjectApi.ts:335` and `ProjectApi.moveEffects` at `:364`).
3. The direct drop on the track header is missing. The header target accepts only NEW effects from the browser (`uuids === null`) and scripts. Existing effects are refused in `drag` (`AudioUnitTrackHeader.tsx:140`) and ignored in `drop` (`:146`, `:155`).
4. Mixer channel strips accept only channel strip reordering (`packages/app/studio/src/ui/mixer/Mixer.tsx:193-196`), no device drops.

## Analysis
The drag source already ships everything needed: `DeviceDragging` sends `{type, uuids, instrument}` for existing effects (`packages/app/studio/src/ui/devices/DeviceDragging.ts:15-27`). Only the header drop handler lacks a branch for `uuids !== null`. `moveEffects` re-homes boxes across any two chain fields and reindexes the source chain, so a cross unit move works with the existing API. A MIDI effect must only land on a unit whose input accepts notes, the same check the header already does for new MIDI effects (`AudioUnitTrackHeader.tsx:148`).

## Possible solution
1. In `AudioUnitTrackHeader.tsx` accept `midi-effect` / `audio-effect` drags with `uuids !== null` in `drag`, refusing a MIDI effect when the unit's input does not accept notes.
2. In `drop`, resolve the boxes (reuse the resolve pattern in `DevicePanelDragAndDrop.ts:183-187` or `CompositeRows.resolveEffectBoxes`), then call `project.api.copyEffects(field, boxes, MAX)` when `DragAndDrop.isCopy(event, data)` and `project.api.moveEffects(field, boxes, MAX)` otherwise, inside `project.editing.modify`.
3. Skip the drop when the boxes already live in that unit's chain (no-op instead of a reorder to the end), or decide that it moves them to the end.
4. Cancel the hover switch on drop as today, so the panel stays where it was.
5. Optionally the same target on mixer channel strips.

## Complexity
small. One drop handler in `packages/app/studio/src/ui/timeline/tracks/audio-unit/headers/AudioUnitTrackHeader.tsx`, existing `ProjectApi` calls, no schema change.

## Open questions
1. Moving an effect to another unit leaves automation tracks that target its parameters on the source unit. Should the move carry those automation tracks along, or is it fine as it is with cut and paste today?
2. Should the dropped instrument (when the drag includes a selected instrument) be ignored on a header drop, or should it replace the target instrument?
