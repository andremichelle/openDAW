## Summary
A user on Zorin OS (Linux) asks for an installable openDAW that runs offline and gives better audio performance than the browser. On 2026-08-21 aribradshaw offered a Windows validated Tauri 2 shell around the existing Studio build (no native commands, COOP/COEP plus CSP, NSIS installer, OPFS kept, no Linux or macOS validation) and asked whether a draft PR would be useful. That offer has no answer in the thread.

## Current state
1. The README lists both an "Offline App" (Tauri) and a "PWA" as open contributor asks (`README.md:60`, `README.md:61`).
2. André built a Tauri desktop app on the branch `tauri-desktop-app` (113 commits not on main, last `5f4063b94`, 2026-10-18). It has a shell that downloads and serves the web build on a fixed loopback port, a native engine with VST3 hosting on macOS, self update, native menus and plugin windows. Plan: `plans/tauri.md` (on main) and on the branch `plans/desktop-freeze.md`, `plans/desktop-issues.md`, `plans/prod-cherry-picks.md`.
3. The branch is frozen since 2026-10-18 (`plans/desktop-freeze.md` on the branch). Reasons listed there: three different system webviews (on Linux the app never started because WebKitGTK hides SharedArrayBuffer), fixes breaking other platforms, Windows tested only in a VM, unstable VST hosting, 30 minute deploys.
4. A PWA plan exists at `plans/pwa.md`, not implemented.
5. An external macOS Tauri wrapper PR #371 was closed on 2026-08-29.
6. An earlier analysis is at `plans/issues/023-native-version.md` (written before the Tauri work, now outdated in its "no Tauri scaffolding" claim).

## Analysis
1. The studio needs `crossOriginIsolated`, SharedArrayBuffer, AudioWorklet and OPFS. A Tauri shell uses the system webview, which is WebKitGTK on Linux, and that engine does not expose SharedArrayBuffer (found during the desktop work). So a plain Tauri wrapper does not run on Linux, which is the reporter's platform.
2. The freeze plan names the precondition for the next attempt: one Chromium engine everywhere (Tauri's CEF runtime or Electron), no native menu bar on Windows and Linux, real test hardware, CI engine tests on all platforms and faster deploys.
3. Better audio performance only comes from a native audio path (the frozen native engine), not from packaging.

## Possible solution
1. Decide between the next desktop attempt and a PWA as a first step. A PWA (`plans/pwa.md`) gives installability and offline use on Linux in Chrome without a new toolchain.
2. For the desktop app, follow "Before the next attempt" in `plans/desktop-freeze.md` on the branch: evaluate Tauri with CEF against Electron, so Linux gets Chromium and SharedArrayBuffer.
3. Answer aribradshaw's offer in the thread, pointing to the frozen branch and the Chromium requirement, so the contribution does not duplicate work.
