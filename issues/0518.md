## Summary
The reporter gets 40 to 50 ms latency on Linux (Fedora Silverblue, GNOME 50 Wayland, PipeWire, Helium 0.17 based on Chromium 153, Ryzen, Focusrite Scarlett Solo 3rd gen). It has always been like this. Audio feels later than MIDI. André said this is outside openDAW and suggested a Chromium bug report. naomiaro pointed to Latency Calibration. The reporter measured a round trip of 115.3 ms and noted that this explains why recordings sounded off beat. The issue is labelled wontfix.

## Current state
1. The AudioContext is created with `latencyHint: 0` and 48 kHz (except Firefox) (`packages/app/studio/src/boot.ts:81-83`). That is the lowest latency a page can ask for. The actual buffering comes from Chromium's Linux backend (PulseAudio API, served by pipewire-pulse) and the PipeWire quantum.
2. The input is opened with echo cancellation, noise suppression and auto gain off (`packages/studio/core/src/io/browser/BrowserAudioInput.ts:315-319`), so no voice processing adds delay.
3. Latency Calibration (Measure Latency) exists and compensates recorded takes with the measured round trip. After calibrating, the reporter's takes should line up. The footer shows the browser reported output latency (`packages/app/studio/src/ui/Footer.tsx:86-92`).
4. The manual page `packages/app/manual/public/latency.md` has only one generic Linux line ("recent systems (PipeWire) behave well").

## Analysis
openDAW cannot change the device buffering of the browser. On Linux, Chromium talks to PipeWire through the PulseAudio compatibility layer, whose default minimum request and quantum are often large (around 20 to 40 ms per direction), and a sample rate mismatch between PipeWire's graph rate and the 48 kHz context adds a resampler. That matches 40 to 50 ms output and about 115 ms round trip. Recording offset is solved by calibration. Monitoring latency is not solvable in the app.

## Possible solution
1. Ask the reporter to confirm that calibrated recordings now line up (the main practical complaint).
2. Extend the Linux section of `packages/app/manual/public/latency.md`: run PipeWire at 48 kHz (`default.clock.rate`), lower `default.clock.min-quantum` and the pipewire-pulse `pulse.min.req` / `pulse.min.quantum` (for example 128/48000 or 256/48000), or start the browser with `PULSE_LATENCY_MSEC` / `PIPEWIRE_LATENCY=256/48000`, and use hardware direct monitoring on the Scarlett for live input.
3. Keep the issue closed as wontfix for the browser part, with a pointer to the manual and to the Chromium tracker.
