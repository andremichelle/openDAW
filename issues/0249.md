## Summary
When a cloud backup finds a project that exists both locally and in the cloud, the reporter wants a compare screen (last edited, track length and similar) and three choices: import the cloud file, create a renamed copy, or keep the local file. Today the reporter deletes all site data and syncs again to get the newer project from another device.

## Current state
1. Cloud project sync lives in `packages/studio/core/src/cloud/CloudBackupProjects.ts`. Projects are matched by UUID, not by name (`:38` to `:47`).
2. Upload: a local project is uploaded only when the cloud copy is missing or older (`:71` to `:75`).
3. Download: only projects missing locally are downloaded (`:150` to `:151`).
4. Consequence: when the cloud copy is newer than the local copy of the same project, nothing happens. The upload skips it because the cloud is not older, the download skips it because it exists locally. Device B never receives the edits made on device A. This is why the reporter wipes local storage.
5. There is no "last synced" record, so a project edited on both devices since the last sync cannot be detected as a conflict. The newer side silently wins on the next upload.
6. The catalog carries only `name`, `modified`, `created`, `tags`, `description` (`:23`). No duration or other content statistics.
7. An older analysis is in `plans/issues/249-file-evaluation-choosing.md`. No commits reference #249.

## Analysis
1. The core gap is a missing third case in the sync: same UUID, cloud newer. That part is a plain bug and the main pain of the reporter.
2. Real conflicts (both sides changed since the last sync) need a per project base timestamp stored locally after each successful sync, otherwise newer local and newer cloud are indistinguishable from a conflict.
3. Same name with different UUIDs means two unrelated projects (for example created separately on two devices). They both survive today, so they are not lost, just duplicated.
4. A compare screen should only use catalog data (`modified`, `created`, `name`) to avoid downloading every `project.od` during sync. Duration would need a new meta field written on save.

## Possible solution
1. In `#download`, also download projects whose cloud `modified` is newer than the local one, not only missing ones. Without step 2 this overwrites local edits made after the last sync, so steps 1 to 3 belong together.
2. Store the cloud `modified` of each project locally after each upload or download (for example in the project meta or a sync record in OPFS).
3. When both local and cloud `modified` are newer than that stored base, collect the project as a conflict instead of syncing it.
4. After the sync pass, show one dialog listing all conflicts with local and cloud dates side by side and three actions per project: use cloud, keep local (upload it), keep both (download the cloud copy under a new UUID and name, for example "Name (cloud)").
5. Optional: add a duration field to `ProjectMeta` on save so the dialog can show length.
6. Tests for the decision table (missing, older, newer, both changed, trashed).

## Complexity
medium. `packages/studio/core/src/cloud/CloudBackupProjects.ts`, project meta storage in studio-core, a new conflict dialog in `packages/app/studio`.

## Open questions
1. Should steps 1 to 3 (take the newer cloud copy when the local copy was not changed since the last sync) ship first as a fix, ahead of the conflict dialog?
2. Should projects with the same name but different UUIDs be offered for comparison too, or only true copies of the same project?
