## Summary
In Safari the peak meter of an armed audio track reacts about 500 ms after the sound (finger snap into the built-in microphone). Chrome and Firefox react at once. It happens on PROD and on main, so it predates the capture rewrite. Recording is not affected: a calibrated take (round trip 115 ms on MacBook Pro speakers and microphone) lines up with the metronome. Also seen once in Safari: the first Measure Latency after opening the input heard nothing (`heard: 0`), the second worked.

## Current state
1. The armed track meter is a separate `MeterWorklet` connected to the capture's `recordGainNode` (`packages/app/studio/src/ui/timeline/tracks/audio-unit/AudioUnitChannelControls.tsx:89-110`, output node from `packages/studio/core/src/io/browser/BrowserAudioInput.ts:103`). While it is connected, the engine's live stream meter for the unit is ignored (`AudioUnitChannelControls.tsx:120-124`).
2. The meter worklet's output is not connected anywhere (`packages/studio/core/src/MeterWorklet.ts:16-26`, default one output). The recording worklet hangs off the same `recordGainNode` and is not connected to the destination either (`BrowserAudioInput.ts:186`).
3. The source is kept pulled by a silent gain to the destination (`BrowserAudioInput.ts:393-396`), added in the capture rewrite.
4. The processor computes the peak per render quantum and publishes it through a `SyncStream` read on every animation frame (`packages/studio/core-processors/src/MeterProcessor.ts:29-64`, `MeterWorklet.ts:28`). There is no smoothing that could add 500 ms on the attack.
5. No fix or branch exists.

## Analysis
Root cause not known yet. What the evidence rules in and out:
1. The source is not 500 ms late in audio context time. The round trip is measured through a recording worklet on the same `recordGainNode` and comes out at 115 ms, so the signal reaches the worklets in time in frame terms.
2. The recording worklet stores frames by position, so it would hide any wall clock delay in how often Safari calls `process()` on a worklet that nobody pulls. The meter shows wall clock behaviour and would expose it. Prime suspect: WebKit processes an `AudioWorkletNode` whose output is not connected to the destination late or in bursts.
3. Second suspect: the `SyncStream` handshake (SharedArrayBuffer plus flag) behaving differently in Safari, for example the reader in `requestAnimationFrame` only seeing new data with a delay.
4. Less likely: the meter is not connected at all in Safari (`outputNode` empty), and what shows is the engine's live stream meter for the unit, which would include engine monitoring latency. That would also explain why the meter moves at all.
5. The `heard: 0` on the first measurement may be the source not running yet right after `getUserMedia` in Safari, a separate start up issue.

## Possible solution
1. Measure in Safari: log `currentTime` and `performance.now()` inside the meter path when the snap peak arrives, and compare with the recording worklet's frame position of the same peak. This separates render delay from display delay.
2. Try connecting the meter worklet's output to `keepAliveSink` (gain 0, already on the destination) or creating it with `numberOfOutputs: 0`, and see whether the lag disappears.
3. Check whether `streamRunning` is true in Safari (meter connected) to rule out suspect 4.
4. If the worklet delivery is the cause, connect both the meter and the recording worklet to the silent sink, and add a test in `CaptureAudio.test.ts` that the meter node is connected to the destination path.
5. For `heard: 0`: wait until the source delivers non silent frames, or retry once, before starting the probe in `measureRoundTrip` (`BrowserAudioInput.ts:250-280`).

## Complexity
unknown. If suspect 2 holds, it is trivial (one connection in `AudioUnitChannelControls.tsx` or `MeterWorklet.ts`). Needs a measurement in Safari first.
