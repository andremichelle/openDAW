## Summary
A system that loads devices into the studio dynamically, to keep boot time short and to allow custom devices from external sources, running in a sandbox so a crashing device cannot take down the studio. A device has a schema, box, adapter, processor, editor and manual. Edge cases: versioning and migration, sandboxing panics, UI restrictions (fixed height, custom menus). Iteration 1: load stock devices dynamically. Iteration 2: an openDAW Device SDK repository for injecting new devices.

## Current state
1. Processor side is already modular. Every stock device is its own Rust `cdylib` side module (`crates/stock-devices/device-*`), linked into the engine at runtime by `packages/studio/core-wasm/src/device-linker.ts` (PIC dynamic linking, host import contract at `device-linker.ts:18`). But all of them are fetched and compiled at boot: `loadEngineModules` fetches the engine plus every entry of `DEVICES` (`packages/studio/core-wasm/src/engine-modules.ts:76`, `:167` to `:178`).
2. An `ExtraDevice` hook (`packages/studio/core-wasm/src/engine-modules.ts:165`) lets a host add device modules by url, used by the offline worker (`packages/studio/core-wasm/src/offline-worker.ts:149`) and tests. No UI path uses it.
3. External devices exist through WebCLAP: plugins load at runtime from a url or a user upload (`packages/app/manual/public/community-webclaps.md`, `crates/stock-devices/device-wclap`). André promotes WebCLAP as the external device format (see #485).
4. Scripted devices (Werkstatt, Apparat, Spielwerk) are the other runtime extension path, user JS run through `packages/studio/core-wasm/src/script-bridge.ts`.
5. The TypeScript side is fully static: boxes are generated from `forge-boxes`, adapters dispatch via the generated `BoxVisitor` (`packages/studio/adapters/src/BoxAdapters.ts:342` for Revamp, 41 device visits), editors likewise (`packages/app/studio/src/ui/devices/DeviceEditorFactory.tsx:419`).
6. `plans/loading-devices-at-runtime.md` exists but describes the removed TS AudioWorklet engine (core-processors, `DeviceProcessorFactory`) and recommends against WebCLAP, so it is outdated.

## Analysis
1. Iteration 1 (lazy stock devices) now mainly means: fetch and link a device side module the first time a project or the user needs it, instead of at boot. The linker already links modules one by one, so the missing pieces are a lazy linking entry point in the worklet, a way to defer `bind_device` until the module is linked, and the main thread knowing which box types need which module. The UI code (adapter and editor) would remain in the main bundle unless they are split with dynamic `import()`.
2. Iteration 2 (third party devices with box schemas) collides with the box graph: box classes, visitor methods and Rust registry entries are generated at build time, and project files must open for everyone. A third party schema would need a generic runtime box type. WebCLAP already covers this case with a generic box (`WclapDeviceBox` with parameter child boxes), which is why the external device question is largely answered by WebCLAP.
3. Sandboxing: side modules share the engine's linear memory, so a panic in a device traps the whole engine call. Real isolation means a separate instance and memory per device (copies per block) or trap recovery that drops the device and keeps the engine running.

## Possible solution
1. Update `plans/loading-devices-at-runtime.md` to the WASM engine, or replace it, and drop the TS engine sections.
2. Lazy linking: keep `DEVICES` as a manifest, compile the engine plus devices used by the loaded project at boot, link the rest on first use (`device-linker.ts`), with the device bound only after its module is ready.
3. Split device editors into dynamic `import()` chunks keyed by box type so the main bundle shrinks.
4. Measure boot first (time spent fetching and compiling the device modules versus the rest) before investing.
5. Keep WebCLAP as the external device SDK path. Trap isolation per device is a separate investigation.

## Complexity
large. Touches `core-wasm` (module loading, linker, worklet protocol), `crates/engine` (deferred device binding), the studio bundle split, and possibly box generation. Cross-layer.

## Open questions
1. Is iteration 2 still wanted given WebCLAP and the community upload, or should the issue be narrowed to lazy loading of stock devices?
2. Is boot time currently dominated by device module compilation? A measurement would decide whether iteration 1 is worth it.
